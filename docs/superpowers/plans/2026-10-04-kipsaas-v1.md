# KipSaaS v1: the open-source SaaS starter kit for Kip Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** draft for /plan-eng-review; do not execute until that pass runs. Execution order within the ecosystem: after Kiption Cloud Milestone A (the revenue path does not depend on this kit) and after the Kip 0.5.0 plan (tags + View seam + busy_timeout) lands.

**Goal:** Ship an MIT-licensed SaaS starter kit on the Kip framework that (1) is the generic engine the private Kiption Cloud consumes, (2) is reusable by every future Hyperion360 SaaS app the same way, and (3) occupies the three open market positions the research identified: a boring no-build stack, a genuinely updateable starter, and production-hardened billing.

**Architecture:** One repo, two consumption modes. The engine (tenants registry, subscription state machine, Stripe integration with pending-window webhook idempotency, signup, rate limiting, provisioning contract, subdomain routing, control web app, `bin/saas` CLI) is a composer package under `KipSaaS\` that apps require; the repo is ALSO a working starter template (a demo SaaS app wired end-to-end) that people can clone and own. The engine code is ported from the twice-engineering-reviewed Kiption Cloud control-plane plan (private repo, internal provenance; this file re-states every load-bearing decision so the kit stands alone).

**Tech Stack:** PHP 8.3, `kip/framework` (^0.5.0 once tagged; `^0.5@dev` + VCS until then), SQLite (registry + per-tenant databases), Stripe over raw HTTPS + HMAC (no SDK), PHPUnit 11. Zero JavaScript in the control plane and demo; zero build step anywhere.

## Market position (research, 2026-10-04, sources in README at execution)

The starter-kit market is overwhelmingly clone-and-own: ShipFast ($199-249), supastarter ($299-1499), SaaSykit ($239-299), MakerKit ($349-649), Larafast ($169-499) all hand buyers a fork; only Laravel Spark ($99-199) ships as a composer dependency with clean upgrades. OpenSaaS (Wasp, MIT, ~16k stars) is the free alternative pressuring the paid tier.

The three biggest unmet demands, with our answer:

| Unmet demand (evidence) | KipSaaS answer |
|---|---|
| Boring, non-React, cheap-to-run stacks (HN on starter kits: "I wish a lot more of these boilerplates didn't go the react route"; production SQLite requested; every PHP kit is Livewire/Filament + Tailwind with a build step) | PHP 8.3, server-rendered, zero JS required, zero build step, SQLite-first, one small VM. The niche is verified unoccupied: no surveyed PHP kit markets no-build/server-rendered/SQLite-first. |
| Genuinely updateable starters (fork rot: ShipFast's own page admits "last update 8 months ago"; Spark's composer model is the lone counter-example) | Engine-as-package: your app is YOUR code; `composer update` pulls engine fixes. The clone-and-own template mode exists too, but package mode is the documented happy path, and Kiption Cloud dogfoods it in production. |
| Trust: maintained, production-hardened billing (ShipFast's 2024 paywall/email-webhook vulnerabilities propagated to every customer; no surveyed kit markets dunning) | Billing built from a production review that caught and fixed the real edge cases: pending-window webhook idempotency (a duplicate arriving mid-processing 500s so Stripe retries instead of losing a paid activation), grace/suspend/resume dunning lifecycle, rollback-on-failure, and a shipped test suite pinning all of it. |

Also table-stakes now and included: AI-context files (AGENTS.md + CLAUDE.md at root; MakerKit/supastarter/Indie-Kit/OpenSaaS all ship agent rules).

## Feature list (the full inventory, and the enough-verdict)

**From the Kip framework (already in the box, zero kit code):** session auth with throttled password reset AND OAuth (Google/GitHub/Microsoft, PKCE); generic admin CRUD panel (schema-introspecting, app-shadowable); fixed-window rate limiting enforced pre-routing; transactional mail (log/mail/smtp, header-injection-proof); S3-compatible uploads; cron scheduler; durable background jobs with a worker; a browser-like test client; codegen scaffolding; OpenAPI generation; VACUUM-INTO backups with retention; HMAC webhook verification; page cache; validated uploads.

**KipSaaS engine (this plan):** tenant registry with the full subscription state machine (pending, verified, active, past_due, suspended, closed; 7-day grace; 30-day retention with purge); plan catalog (free/standard/pro shape, monthly/yearly price ids, per-plan feature flags such as attribution removal); email-verified signup with HMAC single-use tokens (mail-scanner-safe: GET interstitial, POST claim); dual-bucket signup rate limiting (per-IP and per-email); Stripe checkout + billing portal over raw HTTPS; Stripe webhooks with timestamped-signature verification, pending-window idempotency, event rollback, and unknown-tenant acknowledgement; dunning lifecycle (payment_failed -> grace -> suspend -> resume-on-payment -> purge); `ProvisionerInterface` with a reference implementation (per-tenant directory + own SQLite + safe config render via var_export); nginx subdomain map generation with atomic publish and content-idempotent reload; manual-invoicing CLI (`tenant:create`, `provision:tenant`) so you can sell before Stripe exists; the control web app (pricing, signup, verification, billing return, portal-by-email, suspension notice, healthz); CSRF throughout.

**Template + demo (this plan):** a working demo SaaS ("kipsaas demo", a notes app with free/pro plans) proving the engine end-to-end; landing + pricing pages; README quickstart in both consumption modes; DEPLOY.md one-VM guide; Stripe test-mode walkthrough; AGENTS.md/CLAUDE.md; MIT license; shipped test suite.

**Deliberately NOT in v1 (honest scope):** teams/multi-seat (our tenancy model is one tenant = one customer app; seats are a v2 module), usage-based billing (v2; the plan catalog leaves the seam), 2FA (Kip Auth addition, v2), admin analytics beyond the framework CRUD + tenant list, i18n beyond the lang-pack mechanism the framework provides, marketing blog (point at the framework's blog example).

**Enough-verdict:** against the 2026 baseline (research section 4): every [universal] item covered (auth+social, subscription billing, landing page, transactional email, deployment story; the demo covers the blog slot by pointing at the framework example); most [common] items covered (admin dashboard, file uploads via Kip S3, background jobs via Kip Jobs, one-time payments: supported by adding a one-time price row to a plan, tests included); differentiators we OWN (dunning, shipped tests, AI-context, engine-as-package updates, multitenancy-by-installation) versus the two we defer (teams/seats, usage billing). For a v1 aimed at indie PHP developers, this is enough: the deferred items are exactly the ones the research shows buyers complain about as demo-ware, and our differentiators are the ones nobody else has.

## Consumption mechanics (who uses this how)

**No git submodules, anywhere.** Submodules pin without dependency resolution, break on fresh clones (`submodule update --init` is the classic first-day failure), carry no autoloading, and give updates a merge-conflict surface for no benefit. PHP's answer is composer; the starter-market's answer is clone-and-own; KipSaaS supports both properly:

1. **Package mode (how WE use it; the updateable mode):** your app's composer.json carries the VCS repositories (kip, kipsaas) and requires `hyperion360/kipsaas` + `kip/framework`. You implement `KipSaaS\ProvisionerInterface` (stamp your tenant: whatever your app's install shape is) and configure the plan catalog. Engine updates arrive as `composer update` against tags. This is the Spark model, which the market research identifies as the only proven clean-upgrade distribution.
   - Kiption Cloud (private) uses exactly this mode; it keeps only its Kiption-specific provisioner, deploy scripts, and runbook.
   - Future Hyperion360 apps use the same mode; that is the entire reuse thesis.
   - HONESTY about composer resolution (review finding): composer does NOT inherit `repositories` from a dependency's composer.json. Pre-Packagist, EVERY package-mode consumer (including us) must carry both VCS stanzas in their own root composer.json plus `minimum-stability: dev` until tags exist — the README's package-mode quickstart says so explicitly. For STRANGERS via Packagist, `hyperion360/kipsaas` cannot resolve `kip/framework` unless kip is ALSO on Packagist: that is a second, separately-named owner gate ("publish kip/framework to Packagist") in Task 9, adjacent to this repo's own listing. Until both listings exist, package mode for strangers is documented as requiring the two VCS stanzas.
2. **Template mode (how strangers evaluate it; the OpenSaaS mode):** `git clone` this repo, delete the demo app's entity, keep the engine wired, rename, build. You own the copy; the README shows the exact files to touch. Later, `composer create-project hyperion360/kipsaas myapp` once BOTH Packagist listings exist (owner gates, free); create-project in particular cannot pre-add VCS stanzas, so it is gated on the kip listing, not just ours.

**Prerequisite:** the Kip 0.5.0 plan (tags, busy_timeout, View override) must land first; until tags exist the package requires `^0.5@dev` against the VCS repo, exactly as Kiption does today.

**Update discipline for consumers:** the engine never writes your tenant data or your app code; breaking changes follow semver (0.x: minors may break, loudly, in the CHANGELOG, per the framework's versioning policy).

### Task 4: ProvisionerInterface + ReferenceProvisioner

New code (the kit's contract; full):

```php
<?php // src/Provisioner.php
declare(strict_types=1);

namespace KipSaaS;

/** Your app's install ritual. The engine calls these; you implement them once. */
interface ProvisionerInterface
{
    /** Stamp and activate a tenant install. @return array{mail_sent: bool, one_time_password: ?string} */
    public function provision(array $tenant): array;
    /** A suspended customer paid again inside the retention window: restore service. */
    public function resume(array $tenant): void;
    public function suspend(array $tenant): void;
    public function purge(array $tenant): void;
}

/** Your app's data layer: the reference provisioner creates the owner row. */
interface TenantAppInterface
{
    /** Create the tenant's first admin/owner. Return a one-time password the caller hands over out of band. */
    public function createOwner(\PDO $tenantDb, array $tenant): string;
    /** CLI command that seeds a fresh tenant install (schema is the engine's; bootstrap data is yours). */
    public function seedCommand(): string;
}
```

`ReferenceProvisioner implements ProvisionerInterface` — construction contract (the reviewed engine's Task 7 is the port base; the deltas from it are exactly: namespace, the `TenantAppInterface::createOwner` call replaces the Kiption users-table INSERT, and `seedCommand()` replaces the literal `db:blank`):

- `provision(array $tenant): array` — `Slug::normalize` defense-in-depth; refuse existing dir; copy the code tree excluding the reviewed COPY_EXCLUDES (config.php, .git, .gstack, tests, docs, resources, DB files, backups, mail.log, maintenance.lock, nav.json, public/cache, public/uploads, robots.txt); render the tenant config via `var_export` over the app source config (chmod 0600; ALWAYS override `mail.log_path` to the tenant dir); `run(dir, 'migrate')` then `run(dir, $this->app->seedCommand())` via `escapeshellarg`'d proc_open with cwd=tenant dir; `$otp = $this->app->createOwner($pdo, $tenant)`; on ANY Throwable remove the half-built dir (a retry must start clean) and rethrow; then mail the welcome (SMTP config present) or return `['mail_sent' => false, 'one_time_password' => $otp]`.
- `suspend`/`resume`: maintenance-lock file write/unlink (the app's own lock convention, `app/maintenance.lock`).
- `purge`: recursive dir removal.
- Constructor takes `(array $config, Closure $mail, TenantAppInterface $app)` — the app adapter is INJECTED (the Kiption cloud and the demo each bind their own; no app knowledge in the kit).

Tests: the fake-install harness ported and renamed (stub `bin/kip` whose `migrate` builds a scratch table, always-failing stub for cleanup, no-SMTP one-time-password round trip verified against the stored hash, suspend/resume/purge round trip). Commit: `feat: provisioner contract + reference implementation`.
